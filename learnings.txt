What makes slop

No pre-existing mental model of the architecture. The developer lets the AI decide structure, naming, abstractions. The AI will produce something that looks complete but has no coherent design philosophy.
No code review of AI output. AI code is accepted as-is because it runs. Running ≠ correct ≠ maintainable.

Prompting at the wrong granularity. "Build me a document converter" produces slop. "Write a factory method that selects an OCR backend based on this options dataclass" produces a usable component.

What docling did differently

The platform conditionals and version exclusions with bug references in the toml represent accumulated human debugging, not AI output
The architecture (pipeline → backend → model → factory) is a coherent pattern a human designed; the AI filled in implementations

The actual differentiator

AI accelerates writing code. It does not accelerate understanding the problem. Docling's authors understood document parsing deeply before touching a keyboard — IBM Research background, published papers on the topic. The AI helped them write faster, not think.

6. Doc processing using VLMs
Groq vision models are Qwen 3.6 27B and Qwen 3.8 27B. Docling's VLM pipeline is not general-purpose chat — it sends document page images with a specific prompt expecting DocTags or Markdown structured output. The model needs to follow that format faithfully. General vision models like Qwen-VL will attempt it but quality will be inconsistent compared to a model fine-tuned for document parsing like GraniteDocling or SmolDocling.

For your use case (no GPU, no local inference), the most pragmatic path is actually Ollama with smoldocling — it's 256M parameters, runs on CPU in reasonable time, and is specifically trained for this task. The script automatically pulls it. 

GraniteDocling 258M is purpose-built. 258M parameters is tiny by modern standards, runs on CPU, yet outperforms much larger general vision models on document parsing because it was trained specifically on DocTags output from document corpora.

That's the right engineering call: a small specialist beats a large generalist on a narrow task, and is dramatically cheaper to run. Same philosophy as the rest of the project — no bloat, solve the actual problem.

It also explains why the preset system exists. The team controls both the model and the pipeline, so they can ship a preset that wires them together correctly out of the box. With a general model like Qwen-VL you'd have to tune the prompt yourself to get structured output.

8. LangChain doc loaders vs Docling: Why use docling when LC provides them anyway?
The specific problems LangChain's document loaders don't address well:

Table structure — most loaders flatten tables to text. Docling preserves the actual table structure as a first-class object.
Reading order — multi-column PDFs get garbled by naive text extraction. Docling's layout model handles this explicitly.
Mixed formats — LangChain has separate loaders per format, each with different quality levels and dependencies. Docling gives you one unified pipeline across PDF, DOCX, PPTX, HTML, images etc. with consistent output.
OCR integration — LangChain's OCR story is bolted on. Docling's is native to the pipeline.
DoclingDocument format — structured intermediate representation that carries metadata, hierarchy, bounding boxes. LangChain's Document is just text + metadata dict.

LangChain also now has a DoclingLoader — which uses docling under the hood. That's essentially IBM's answer to the question: they didn't compete with LangChain on orchestration, they made themselves the ingestion layer that LangChain calls.

So the actual answer is: LangChain 1.x solved the orchestration mess, and outsourced the hard document parsing problem to docling.

Claude Q: So modern prod-grade workflows would be built using LC+LG, but use Docling and other specialised libraries for the individual tasks

Claude A: Exactly. That's the architecture pattern emerging in serious AI engineering shops right now:

LangGraph — orchestration, state management, agent loops
Docling — document ingestion and parsing
Chroma/Milvus/Weaviate — vector storage
Rerankers (Cohere, ColBERT) — retrieval quality
Guardrails/Rebuff — safety and prompt injection defense
LiteLLM — LLM provider abstraction

Each component is best-in-class for its narrow problem. LangGraph is the glue, not the substance.

The anti-pattern is using LangChain's built-in version of everything — their PDF loader, their vector store wrappers, their retriever — because they're generalist implementations optimized for demos, not production edge cases. They get you to a working prototype fast, which is their actual value. Then you replace components one by one as you hit their ceilings.

Claude A2:
LC components that are production-grade and remain standard:

LangGraph — the orchestration layer is genuinely good. Used in production at serious shops.
langchain-core primitives — Document, BaseMessage, RunnableLambda, the LCEL pipe operator. These are thin, well-designed abstractions.
Provider integrations — ChatOpenAI, ChatAnthropic, ChatBedrockConverse etc. These are thin wrappers around provider SDKs. No reason to bypass them.
with_structured_output() — solid, uses native tool calling under the hood.

LC components where you hit ceilings in production:

Document loaders — PyPDFLoader, WebBaseLoader etc. are fine for prototypes. For production PDFs with complex layouts, tables, or scanned content, Docling or Unstructured are measurably better.
Text splitters — RecursiveCharacterTextSplitter is a blunt instrument. Semantic chunking, layout-aware chunking, and document-structure-aware chunking all outperform it for RAG quality.
Vector store wrappers — the abstraction is shallow as you've already seen. Fine for CRUD, breaks down for advanced filtering and hybrid search.
Built-in retrievers — MultiQueryRetriever, ContextualCompressionRetriever are solid concepts but fixed implementations. Production systems usually need tuned reranking (Cohere, ColBERT) for precision.
Memory — LC's built-in memory is largely deprecated. LangGraph's state management replaced it properly.
